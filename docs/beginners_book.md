1.1 この教材のねらい

7. このコース「要素技術とモデルを開発に使おう」は、次のことを主眼に作成してあります。

• コードを書くのにモデル図が役に立つことを実感してもらうこと。
• 要素技術をモデル図に反映する方法について学ぶこと。

1.2 ねらいの背景にあること

1.2.1 記法やプロセスは知られているが使われていない

8. みなさんは、ソフトウェアの開発には設計が必要で、ソフトウェアの設計では主にUMLやSysMLを

使って作成したモデルを使うことを知っているでしょう。 開発プロセスについても、業務を通じて、

あるいは大学の講義などで知っている人も多いでしょう。

9. その一方で、いまだに多くの方が、「ソフトウェアの場合、設計したって、その後で考えながら実装

しなくてはならない。だから、設計書（あるいはモデル）は詳細を書けない（あるいは書いていられ

ない、書かなくてかまわない）」という考え方を持っています。

1.2.2 他の分野では設計は実装に欠かせないもの

10. しかし、他の工学分野はそうではありません。そのような考え方では、他の人や他の会社に頼んで作

ってもらうときに齟齬が生じ、うまくいかないことがわかっているからです。 たとえば、ギター・ア

ンプが壊れれば、回路図をみながら修理できます。 木造の家を建てるとき、工場から部材が出荷され

る段階で、どこに使うのか決まっており、必要な加工も済んでいます。 同じ図面の家を2軒、別のチ

ームが建てたとしても、同じ家が建ちます。増改築するときには、図面をみながら検討できます。

11. ソフトウェアの場合はどうでしょうか。みなさんのコードは、設計書で分けてほしいと指示した場所

できちんと分けられていますか。設計書に使われていることばがコードの中に見つけられますか。コ

ードに不具合が見つかった時、それが設計時の問題か実装時の問題か、設計書をみて判断できます

か。 そうはなっていないという場合が、まだまだ多いのではないでしょうか。

1.2.3 ソフトウェアの実装に設計が役立つことを実感しよう

12. われわれは、ソフトウェアの設計が他の分野のように有効に活用できていないのは、まだ多くの人が

次のような状況にあるからではないかと考えました。

• 「設計があったほうがよい」「設計があると助かる」という気持ちになったことがない。
• 本来設計で済ませるべきことを、実装時に考えながら決めている。

13. たとえば後者を家の建築に当てはめるなら、建築現場で工法を思案したり、部材を測ったりしている

ような状況でしょう。

14. では、どうすればこのような状況から抜け出せるのでしょうか。 われわれは、みなさんに設計やモデ

ルが実装の役に立つことを実感してもらうことが必要だと考えました。 設計や記法を知っていても、

便利とか有効だとか感じていなければ、使わないのも当然のことだからです。 このような経緯で、こ

の教材「要素技術とモデルを開発に使おう」は用意されることになったのです。

1.3 この教材で学んでほしいことはなにか

15. モデリング演習を通じて学んでほしいのは、次のようなことです。

• 課題があったとき、それをモデルで表現する、モデルで考える
• コードはモデルに合わせて書く
• 要素技術をモデルに組込むことで結びつける

16. このようなことを学んでもらうため、以下のような演習を提供します。

• コードを書くのに図が使えることを実感します。
• 要素技術の実験結果をモデル図に組込む方法を使ってみます。

17. 以下のことは、コースでコードを書くのに図が使えることを知った上で、技術教育2の 「 開発プロセ

スに沿って開発しよう 」 で学ぶことにします。

• オブジェクト指向の考え方を実践する。
• UMLの記法を設計に使ってみる。
• 開発プロセスに沿って開発を進める。

1.4 トレーニングの進め方

1.4.1 演習の構成

18. 演習は以下のように進めます。

1. コードのやっていることを表すのにモデル図が使えることを実感します。
◦ サンプルのコードをそのまま元にモデル図で表してみます。
◦ モデル図を使って現状を見直し、それに合わせてコードの構造も見直します。
2. 要素技術を実験し、アプリケーションに組込んでみる
◦ 簡単なライントレーサーの課題を挙げ、要素技術の必要性を感じます。
◦ 課題に対処するための要素技術として、比例制御を使えるかどうか実験します。

1.4.2 なぜ開発プロセスに沿って演習しないのか

19. この教材における演習は、背景で示した考え方に立って、次のようなことを原則とします。

• この教材の演習では RasPike-ART 環境を中心に進めて行きます。etrobo環境を使用する人は、
適時読み替えて学習を進めてください。どちらの開発環境でも、設計モデルが実装に役立つこと

を実感するという考えは共通して有効でしょう。

• 開発プロセスに沿って設計から実装へ進むのが一般的ですが、あえてコードを図で表すところか
ら始めています。なぜなら、コードの現況をモデルで表すことは、モデルとコードのつながりを

デルとコードは対応づいていることを意識できるようにするためです。

• 要素技術については、まず実験して方式を決めます。そこから得られた知見をクラスやメソッド

に仕立ててモデルに組込み、その後モデルに対応するようにコードを作成します。

SSHでのファイル転送

59. SSHでのファイル転送は、scpコマンドを使います。scpコマンドは、SSHで接続した相手にファイル

からRasPiにファイルを転送する場合も使えます。

60. scpコマンドは、sshコマンドと同じように、接続先のIPアドレスを指定して実行します。 scpコマン

CONSOLE

% scp test.c pi@192.168.11.17:work
pi@192.168.11.17's password:

% scp -r testdir pi@192.168.11.17:work
pi@192.168.11.17's password:

CONSOLE

113. const 宣言によって、繰り返し処理の間隔に使う定数 duration を宣言し、初期値として2,000,000マ

イクロ秒（2秒）を設定した。

114. sleep メソッドを使って duration に指定した時間だけ処理を停止する。

115. duration が定義してある場所は、繰り返し間隔の値を使う場所ではなく、別の場所になっています。

116. 2箇所に分けて書く代わりに、 リスト 3.11 のように、使いたい箇所で繰り返し間隔を直接書いても動

118. しかし、この書き方には、2つ問題があります。

1つ目は、即値を書くと、どんな意味の値なのかわからなくなることです（たとえば、その値がマイ

クロ秒なのか、ミリ秒なのか、カウント数なのかなど）。 また、たまたま同じ値を、異なる場所で別

の用途でも使っていた場合、その値が修正の対象なのか判断しづらくなります。 名前をつけた値を使

っておけば、 clock に渡しているのは「繰り返し間隔のための時間」ということがわかり、他の値と

も区別しやすくなります。

119. 2つ目は、時間間隔を変更したいときです。 使っている箇所をすべて修正するよりは、定義している

値を1つ変更するほうがずっと簡単で安全です。 また、const 宣言をつけた定数として定義している

ので、変更しようとすれば、コンパイラが検出してくれます。 即値を使った場合には、誤って書き換

えてしまっても、検出できないでしょう。

7.4 比例制御（P制御）

7.4 比例制御（P制御）

264. sample03 の走り方は、ライン上とラインから外れているときの2種類の動作でできていました。 ライ

ンから完全に外れたときと、ラインの中に完全に入ったときの2つの値を使っているので、振れ幅が

大きくぎこちないですね。 もっと滑らかに走るには、ラインの境目に沿って走るよう、境目から大き

く外れる前に動作を変化させる必要がありそうです。 つまり、2つの値を使う代わりに、境目の値（

白でも黒でもない）を1つの目標値にして、そこからのズレを小さくするのです。

265. 比例制御（Proportional制御、P制御）は、あらかじめ決めておいた目標値とセンサーから得た測定

値のズレの大きさに比例した操作量を使う制御方法です。 sample03 に当てはめると、測定値はカラー

センサーの取得値で、目標値はラインの境目、つまり白と黒の中間の値です。 この方法なら、白か黒

か判定に使っていた値よりも境目に近い変化を扱うので、その分振れ幅が小さくなるはずです。

266. 比例制御について考えるために、sample03 でのラインの境界付近のカラーセンサーの値の変化を大き

く拡大してみましょう。

• ラインの境界付近では、カラーセンサーの取得値は、白からの反射と黒から反射が混じったもの

になっている。

• ラインに近づくほど黒から反射が多くなり、ラインから外れるにつれて白からの反射が多くな

る。

267. つまり、測定値を白か黒かの2値に分けず、これらの間の値も使い、目標値もラインの境界付近の値

（白と黒の間の値）にすれば、動作がスムーズに走ってくれるそうだと考えたわけです。

• 動作を切り替えるとき、PWM値を 0 と走行時の値の2種類とせず、測定値の大きさに応じて減ら

してみる

268. これでどうやら、カラーセンサーの測定値と比較する目標値の差の大小に応じて左右のモーター

のPWM値を加減すれば、ズレに応じて旋回の度合いを調整できそうです。

8.2.1 滑らかに走る方法を考えてみよう

272. もう少し滑らかに走れるようにするには、どんなことを考えればよいでしょうか。

273. sample03 の走り方は、ライン上かライン外かで動作が2種類だけです。 ラインからたくさん外れたと

きも、少ししか外れていないときも、同じ動作になります。 走り方を滑らかにするには、ラインから

外れた度合いに応じて処理を変化させる必要がありそうです。

274. そこで、ラインの境界付近でのカラーセンサーの値の変化を考えてみます。

• カラーセンサーの取得値は、白と黒の間の値で徐々に変化しているのではないか
• ラインの境界付近では、ライン上の値寄りの値になっていないか
• 白と黒の間の値が取得できれば、その分旋回する度合を小さくできないか

きそうです。

た度合いとみなす

276. どうやら、カラーセンサーの測定値と比較する目標値の差の大小に応じて左右のモーターのPWM値

を加減すれば、ズレに応じて旋回の度合いを調整できそうです。

A.1 クラス図とコードの対応

294. クラス図は、システム内の各クラスについて、その役割、責務、インターフェイスに注目し、クラス

内部の実装詳細を隠蔽した「ブラックボックス」として捉えることで、システムを構造に関して抽象

化します。 この抽象レベルでの検討は、クラス間の連携、責務分担、依存関係などの構造を図式化、

視覚化することで、実際にコードを書く前にアーキテクチャの健全性を確認するうえで非常に重要で

有効な検討になります。 チーム内で設計思想（設計方針や仕様）を共有し、具体的な実装コードに先

立ち、各自の理解を統一するための「共通言語」となり、実装前の合意形成ができます。 このクラス

図とオブジェクト指向プログラミング（OOP）との対応づけには、以下の点で大きな意義と必要性が

あります。

• コードとの対応づけは、抽象設計と具体実装の橋渡しになります。このとき、設計した情報が実

装において失われないようにすることが必要です。

• 設計とコードが対応していれば、レビュー時に設計意図を確認しながらコードを修正でき、誤解
や重複作業が減ります。逆を言えば、実装の構造や振舞いが、設計の構造や振舞いに立ち戻るこ

とができることになります。

• コードとの対応づけにより、オブジェクト指向設計の概念と実際のプログラムコードの関係を直

感的に理解しやすくなります。

295. 設計とコードの対応づけができれば、つぎのような効用があります。

296. 実行時動作のシミュレーションによる検証

クラス図を基にOOPの実装を進めることで、各クラスのインターフェースや連携パターンが、実際の

プログラミング環境でどのように振る舞うかを、プロトタイプや疑似コードを通して先行検証できま

す。 つまり設計段階の仮説を実際にコードを実行した際の動作検証が容易になります。

297. 設計意図の実装反映とプロセスの最適化

クラス図を基にOOPの実装を進めることで、設計の意図を保持したままコード実装へ移行できます。

実装すべきフレームワークやシステムの大枠がプロトタイプや疑似コードを通して事前に設計意図の

検証が可能になります。 つまり設計から実装へのシームレスな移行が容易になります。

298. OOPの実践的な適用と検証

クラス図とOOPの対応づけを行うことで、抽象化された設計が具体的なコード（OOP）に落とし込ま

れる際の実現可能性が判断できます。 オブジェクト指向の「カプセル化」、「抽象化」、「継

承」、「ポリモーフィズム」が正しく機能するかを検証することができます。 また、オブジェクト間

の「メッセージパッシング」や動的な振舞い、インスタンス生成のタイミングなど、実行時の動作に

ついても、プロトタイピングによるシミュレーションを通して評価することができます。

A.4 関連関係（Association）

311. 関連関係は、異なるクラスのインスタンス間における構造的なつながりを表します。 これは、一方の

クラスのオブジェクトが他方のクラスのオブジェクトと何らかの形で関係を持つことを意味します。

関連は、オブジェクトが互いにメッセージを送信したり、操作を呼び出したり、互いに認識し合った

りするなど、様々な形で現れます。

312. 関連関係は、以下のような特性を持ちます。

多重度（Multiplicity）

関連するインスタンスの数を指定します（例：1対1、1対多、多対多）。

誘導可能性（Navigability）

一方のオブジェクトから他方のオブジェクトへの参照が可能かどうかを示します。

誘導不可能（Non-navigable）

一方のオブジェクトから他方のオブジェクトへの参照が不可能ということを示します。

役割（Role）

関連の各端におけるクラスの役割を記述します。

集約（Aggregation）とコンポジション（Composition）

より強い形式の関連であり、全体と部分の関係を表します。

関連クラス（Association Class）

関連自体が属性や操作を持つ場合に用いられます。

A.6 コンポジション関係（Composition）

322. コンポジション関係は、クラス図における集約の一種であり、より強い形式の「全体と部分」の関係

A.7 汎化関係（Generalization） もしくは継承関係（Inheritance）

330. クラス図における継承元の、より一般化されたクラス（矢印側のクラス）を「親クラス」「基底クラ

つことができます。 サブクラスがスーパークラスの一種であるという関係性を意味します。

331. 汎化（もしくは継承関係）を利用することで、 スーパークラスで定義された属性や操作をサブクラス

で再定義（オーバーライド）したり、追加したりすることができます。 これにより、コードの再利用

性が高まります。

ん。 抽象クラスは、サブクラスに共通のインターフェイスを定義するために使用されます。 抽象ク

A.8 インターフェイス関係

A.8.1 インターフェイス関係の概要

336. UMLのクラス図におけるインターフェイスは、クラスやコンポーネントが提供するサービスの仕様

を定義するものです。 インターフェイス自身は振る舞いの実装を持たないで、操作（メソッド）のシ

グネチャ（名前、引数、戻り値の型）を定義します。 クラスは、一つまたは複数のインターフェイス

を実現（実装）することで、それらのインターフェイスが規定する振る舞いを保証します。 インター

フェイス関係は、システムの疎結合性を高め、柔軟で保守性の高い設計を可能にする重要な概念で

す。

A.8.2 インターフェイス関係の主要な側面

インターフェイス（Interface）

• Classifier の一種であり、振る舞いの仕様を定義します。
• 属性（静的属性の定数）を持つこともありますが、通常は操作（operation）の定義が主体です。
• キーワード «interface» を付与したステレオタイプで表現します。
• あるいは提供インターフェイス（ロリポップ記号）で表現されます。

インターフェイス実現（Interface Realization）

• クラスが特定のインターフェイスを実装することを表す関係です。
• 実現するクラスから実現されるインターフェイスへ向けて、破線に白抜きの三角を付けた線で表

現します。

• あるいは提供インターフェイス（ロリポップ記号）を使用する場合は、実現するクラスに実線で

接続します。

• Interface Realization [Class] は Abstraction の特殊化です。

使用（Usage）

• あるClassifier（通常はクラス）が、別のClassifier（通常はインターフェイス）が提供するサー

ビスを利用することを示す依存関係の一種です。

• 使用するClassifierから使用されるインターフェイスへ向けて、破線の矢印で表現します。
• 要求インターフェイス（ソケット記号）を使用する場合は、要求するクラスに実線で接続しま

す。

提供インターフェイス

• クラスやコンポーネントが外部に提供するインターフェイスは提供インターフェイスと呼ばれ、

実線と丸印のロリポップ記号で示されます。

        currentState = nextState;                   // つぎの状態の設定
   }
